# Baseline methodology report

How each of the four baselines (B1–B4) produces a `RunArtifact`, why some
columns in the per-system table are populated and others are zero, and what
the zeros do — and do not — mean for the comparison.

---

## 1. The shared scoring path

Every system in this experiment is scored by the same function,
[`experiments/common/metrics.py::score`](../../common/metrics.py), against
the same `RunArtifact` shape:

```python
RunArtifact = {
  "system":             str,            # mas / b1 / b2 / b3 / b4
  "intent_id":          str,
  "topology":           dict | {},      # the 5G topology blueprint
  "config_artifacts":   list[dict],     # per-VNF helm_values
  "validation_report":  dict | {},      # populated by harness if the runner left it empty
  "deployment_results": list[dict],     # only non-empty for systems that helm-install
  "intervention_log":   list[dict],
  "wall_clock_s":       float,
  "deployment_wait_s":  float | None,
  "error":              str | None,
}
```

The harness in [`experiments/experiment_2/run_comparative.py`](../run_comparative.py)
treats every system uniformly:

1. Call `runner.run(intent, deploy=…)` to obtain a `RunArtifact`.
2. If `system in {mas, b3}` and `--deploy` is set, attempt a real cluster
   deploy and stamp `deployment_wait_s`. *In the current configuration only
   MAS actually helm-installs; B3 is treated as artifact-only at the harness
   layer (see § 4.3 below).*
3. Run the **same** static policy validator
   ([`agents/policy_validator.py::run_static_policies`](../../../agents/policy_validator.py))
   on every system's `config_artifacts` so that policy and config-error
   metrics are computed against the same five checks for everyone.
4. Score the artifact through `metrics.score`.

This means **the only thing that differs between systems is how the
artifact is generated** — the scoring is identical.

---

## 2. The six metrics, in one paragraph each

For full definitions see § 4.6 of the thesis chapter. In short:

- **Deployment time (s)** — `wall_clock_s + deployment_wait_s`. Reflects the
  full latency from intent submission to "all pods Ready" *for systems that
  deploy*; for non-deploying systems it reflects only artefact-generation
  time (or, for B1/B2 where the runner overrides `wall_clock_s` from a
  calibrated distribution, the simulated operator/MANO time).
- **Config error rate** — fraction of `config_artifacts` whose `helm_values`
  fail `helm template --validate`. Computed by
  [`experiments/common/config_validation.py`](../../common/config_validation.py).
- **Resource accuracy** — `1 − mean(|generated − optimal| / optimal)`,
  clipped to [0, 1], where the optimum is computed from
  `vnf_resource_profiles.yaml` applied to the intent's
  `structured_features`.
- **Human interventions** — `gates_triggered + critic_rejected + policy_FAILs`.
  For B1 the `intervention_log` is generated by the calibrated emulator;
  for B2/B3/B4 the count comes from the harness-side critic + policy
  validator running on the artifact.
- **Intent-to-deploy accuracy** — composite binary, `1` iff
  `deployment_success_rate == 1.0 ∧ vnf_coverage ≥ 0.8 ∧
  policy_decision == GO ∧ critic_approves`.
- **Policy violation rate** — `1 − policy_pass_rate`, where pass means
  `status == PASS` (PASS-or-WARNING is **not** sufficient).

## 3. The five system runners

### 3.1 MAS — the LangGraph multi-agent system

The runner ([`experiments/common/runners.py::MASRunner`](../../common/runners.py))
streams the LangGraph state machine to completion and lifts the final
state into a `RunArtifact`. With `--deploy`, the deployer node performs
real `helm install` against the OAI cluster at 172.21.25.9 (namespace
`oai-5g`), and the harness additionally polls the cluster until every
release's pods are Ready. With `--no-deploy`, the deployer node is
replaced by a no-op so the rest of the pipeline runs without touching
the cluster.

MAS is the **only** system that produces a non-empty
`deployment_results` list in the data set used for this thesis.

### 3.2 B1 — Manual operator, calibrated stochastic emulator

[`experiments/baselines/b1_manual.py`](../../baselines/b1_manual.py)

Real human runs across 180 trials are not feasible (≈100 hours of
operator time per system), so B1 is a **calibrated emulator**:

1. A pilot study (literature-derived in the current calibration; the
   protocol for replacing it with a real 2-hour pilot is documented in
   [B1_PILOT_GUIDE.md](../../baselines/B1_PILOT_GUIDE.md)) provides the
   timing distribution per VNF, the iteration count, the per-VNF
   intervention count, and the per-VNF config-error rate.
2. The emulator copies the standard chart values
   ([`charts/oai-5g-core/oai-5g-basic/values.yaml`](../../../charts/oai-5g-core/oai-5g-basic/values.yaml))
   verbatim — no intent translation.
3. With probability `error_rate`, a stochastic error is injected into a
   VNF's helm_values (omitted probe, missing resource limits, wrong
   PLMN, "latest" tag, …).
4. `wall_clock_s` is overridden to a draw from
   `Normal(per_intent_understanding + 7·per_vnf_edit + iters·helm_install,
   …)`, conditioned on the calibration parameters.
5. `intervention_log` is populated with one entry per simulated HITL
   moment, drawn from `per_vnf_intervention_count`.

The emulator is **deterministic given a seed**, which the harness
derives from `(intent_id, rep)` so re-runs reproduce.

`deployment_results` is **always empty** — the emulator never claims to
have actually helm-installed anything.

### 3.3 B2 — OSM/MANO literature stub

[`experiments/baselines/b2_osm_stub.py`](../../baselines/b2_osm_stub.py)

Standing up a real OSM stack and onboarding NSDs/VNFDs would be
infrastructure work whose noise dominates any measurement and, more
importantly, whose result would not generalise off the specific OSM
release used. Per the experimental plan, B2 is a **literature-anchored
stub**:

- Timing distribution from Yousaf et al. (2017), Benzaid & Taleb
  (2020), and one 5G-PPP report. 8–12 minutes per NS deployment, hence
  the ~3940 s mean.
- A fixed NSD/VNFD library — the same 7 core VNFs deployed for every
  intent, with **no scaling against `ue_count`, `throughput_gbps`,
  `slices`, or `ha_required`**. This is the methodologically important
  point: OSM literally does not derive resources from the intent.
- A lower stochastic config-error rate than B1 (calibration says ~6 %
  vs B1's 12 %), reflecting OSM's own descriptor validators catching
  many typos before they reach Helm.
- A higher per-VNF intervention count than B1, reflecting NSD authoring
  being more interaction-heavy than direct Helm editing.

Honest framing for the thesis (§ 5.2 caveats): "literature-anchored
stub, not measured." `deployment_results` is always empty.

### 3.4 B3 — Static manifests + HPA scaffold

[`experiments/baselines/b3_static_hpa.py`](../../baselines/b3_static_hpa.py)

This baseline is included to represent "what you get with vanilla
Kubernetes if you do not do intent translation at all":

1. Read the standard OAI Helm values
   ([`oai-5g-basic/values.yaml`](../../../charts/oai-5g-core/oai-5g-basic/values.yaml)).
2. Pick replicas and per-VNF `cpu_m / memory_mi` from a **fixed linear
   table keyed only on `intent.ue_band`** (50 / 200 / 500). No LLM, no
   slice planning, no scenario reasoning.
3. Emit a `helm_values.autoscaling` block (`enabled, minReplicas,
   maxReplicas, targetCPUUtilizationPercentage`) for every "scalable"
   VNF.
4. Build a topology and `config_artifacts` in the same shape as MAS / B4.

B3 is in `DEPLOYING_SYSTEMS = {"mas", "b3"}` in principle, but the
harness's `deploy_artifact_and_wait` returns immediately for B3
because the B3 runner returns `deployment_results=[]` — see § 4.3.

### 3.5 B4 — Single-agent LLM

[`experiments/baselines/b4_single_llm.py`](../../baselines/b4_single_llm.py)

Collapses the MAS planner + resource allocator + VNF configurator
into a single LLM call. To keep the comparison fair:

- The system prompt is the **same** Network Planner system prompt as
  MAS, *extended* (not weakened) with `B4_EXTENSION` to demand topology
  + per-VNF `resources` + per-VNF `helm_values` in one JSON response.
- The same base model (`gpt-oss:120b`) and the same JSON-extraction
  helper are used.
- There is no separate validation step **during** generation — but the
  policy validator runs **on the output** (via the harness, § 4.2).
  That asymmetry is the whole point of B4: it shows what is lost when
  the multi-agent pipeline is reduced to a monolithic prompt.

`wall_clock_s` is the real LLM call duration. `deployment_results` is
always empty — B4 generates artefacts but does not deploy them.

## 4. Why some columns are zero

### 4.1 `intent_to_deploy_accuracy = 0` for B1, B2, B3, B4 — *by construction*

This is the most important zero in the table. The composite is
defined as:

```
intent_to_deploy_accuracy = 1
  iff deployment_success_rate == 1.0
   ∧ vnf_coverage ≥ 0.8
   ∧ policy_decision == GO
   ∧ synthetic_critic_approves
```

`deployment_success_rate` requires non-empty `deployment_results`. None
of B1–B4 produces `deployment_results`, so `deployment_success_rate ≡
0` for all of them, so the AND is always 0. **The 0.000 column is not
"the baselines were judged worse" — it is "the baselines do not deploy
in this experiment."** This is documented as a methodology caveat in
both [REPORT.md](REPORT.md) § 3 and the thesis chapter § 5.3.5.

The two ways to read this column:

- *As stated in the metric definition*: the only system in the
  experiment that converts an intent into a Ready 5G core is MAS.
- *Diagnostically*: each baseline's individual sub-conditions are
  tracked separately in `components.intent_accuracy_components` in
  `raw.jsonl` and reported in [REPORT.md](REPORT.md) so reviewers can
  audit which constraints each baseline would have hit even if it did
  deploy.

### 4.2 `config_error_rate = 0` for B1, B2, B3 — chart values are valid

`config_error_rate` is computed by running each artifact's
`helm_values` through `helm template --validate` against the matching
chart. It is the fraction that fail.

- **B1** copies the OAI basic chart values verbatim and only mutates
  fields where it injects a stochastic error. Even when an error is
  injected (e.g. `imagePullPolicy: latest`), the *helm template* still
  succeeds — the error is captured by other metrics (Resource accuracy
  via wrong sizes, Policy violation rate via the `image_tags` check).
  The `helm template --validate` step is a syntactic check, not a
  semantic one.
- **B2** synthesises the helm_values that an OSM OAI plugin would
  produce, sized from a fixed default table. Same story: syntactically
  valid, semantically wrong on `resource_accuracy`.
- **B3** starts from the same chart defaults and only fills in
  resources, replicas, and an autoscaling block. Always template-valid.

The B4 column is **0.869**, not 0, because the single LLM
hallucinates field shapes (wrong key paths, missing `nfimage`,
malformed YAML strings) far more often than the templated
configurators. This is the largest standardised difference in the
experiment apart from the literature-distance comparisons on B2
(d = −6.25 against MAS's templated configurator).

### 4.3 `deployment_time_s = 0` for B3 — harness layer skips deploy

B3 is in `DEPLOYING_SYSTEMS` and would in principle be deployable, but
two layers stop it from registering deploy time:

1. The B3 runner does **not** call `helm install` itself — it returns
   `deployment_results=[]`.
2. The harness's `deploy_artifact_and_wait` is gated on
   `if not artifact.get("deployment_results"): return` — so it never
   stamps a non-zero `deployment_wait_s`.

Combined with B3's runner returning a tiny `wall_clock_s` (the few
hundred microseconds spent reading the chart and indexing the
static table), Metric 1 for B3 is essentially 0.0 ± 0.0.

The plan reserved real installs for MAS to keep the cluster
single-tenant and to avoid concurrent-Helm contention; B3's role is
strictly artefact-only at this layer. The thesis caveat (§ 5.3.1) makes
this explicit: B3's 0 s is *artefact generation only*, not a real
deployment time.

If we wanted B3 to actually deploy, two changes are needed: serialise
runs (no concurrent helm installs) and have the B3 runner emit a real
`deployment_results`. Both are noted in the plan as out of scope.

### 4.4 `policy_violation_rate = 0` for B3 and B4 — they don't trigger the static checks

`policy_violation_rate = 1 − policy_pass_rate`, where
`policy_pass_rate` is the fraction of the **five** static policy
checks that return `PASS` (PASS-or-WARNING is not sufficient).

- **B3's** `_build_helm_values` fills in `nfimage`, `exposedPorts`,
  `start`, `readinessProbe`, `livenessProbe`, `resources.define = True`
  with proper `requests.nf` and `limits.nf` blocks, and pinned image
  versions (`v2.1.0`). It does **not** explicitly set
  `podSecurityContext.runAsUser`, so the `root_containers` check sees
  no `runAsUser=0` field and returns PASS rather than WARNING. All
  five checks PASS → `policy_pass_rate = 1.0` → `violation = 0.0`.
- **B4's** LLM, when its output is well-formed enough to score, also
  rarely emits an explicit `podSecurityContext` block, so the same
  PASS path applies. (When the LLM's output is malformed, it shows up
  as `config_error_rate`, not `policy_violation_rate`.)
- **B1** scores 0.131 because the stochastic error injection
  occasionally produces violations the static checks catch (e.g.
  missing resource limits, "latest" image tag).
- **B2** scores 0.013 — its rarer injected errors very occasionally
  trip a check.
- **MAS** scores a constant **0.200** because the MAS VNF Configurator
  *deliberately* sets `podSecurityContext: {runAsUser: 0, runAsGroup:
  0}` to match the OAI charts' actual runtime behaviour, and the
  `root_containers` check fires WARNING on every run. WARNING ≠ PASS
  in the metric, so 1 of 5 checks "fails" → 0.20.

This metric should therefore be read with a strong caveat: it
penalises *being honest about chart behaviour*. A strictly-applied
check would also flag B3 and B4 as 0.20, since the OAI charts they
inherit from do run as root at runtime — they just don't surface that
fact in the helm_values dict. The thesis chapter § 5.3.6 says this in
prose. The bottom line: the MAS-vs-B3 / MAS-vs-B4 d = +10.0 numbers in
the pairwise table reflect a defensible-style policy (`be explicit
about runAsUser`) rather than a real safety regression.

### 4.5 Where the *non-zero* baseline numbers come from

Only `deployment_time_s`, `resource_accuracy`, `interventions`, and
sometimes `policy_violation_rate` carry signal for the baselines:

| Metric | B1 | B2 | B3 | B4 |
|---|---:|---:|---:|---:|
| Deployment time (s) | 1037 (calibrated draw) | 3943 (literature) | 0 (artefact-only) | 30 (real LLM time) |
| Resource accuracy | 0.114 (chart defaults) | 0.249 (fixed table) | 0.352 (UE-band table) | 0.499 (LLM sizing) |
| Human interventions | 9.28 (per-VNF count) | 17.42 (NSD authoring) | 0.44 (deterministic) | 0.14 (single shot) |
| Policy violation rate | 0.131 (stochastic) | 0.013 (rare) | 0 | 0 |

The ordering on Resource accuracy is methodologically informative on
its own: B4 (0.499) > B3 (0.352) > B2 (0.249) > B1 (0.114). Even a
monolithic LLM that *attempts* intent translation recovers more of
the intent's resource shape than a UE-band-keyed lookup table; the
table beats a fixed descriptor library; the descriptor library beats
a noisy human emulator. MAS's 0.732 sits an additional ~23 percentage
points above B4 — that gap quantifies the value of the dedicated
Resource Allocator agent.

---

## 5. Summary

The five-system table is fair to compare on **Resource accuracy**,
**Deployment time vs B1/B2**, and **Human interventions** without
caveats. It is fair on **Config error rate** for the B4 column only;
the B1/B2/B3 zero is "their artefacts pass `helm template`, the work
they do wrong shows up in *other* metrics." It is **never fair** on
**Intent-to-deploy accuracy** as a horse-race — that column reports
"only MAS deploys in this experiment" — but the four sub-conditions
are reported separately so readers can see where each baseline would
have stood if it did. **Policy violation rate** is fair against B1
and B2 but penalises MAS's explicitness about runtime behaviour for
the B3/B4 comparison; the chapter discussion explains this inline.

Original raw data: `results/full_bmin/raw.jsonl` (post-B-min) and
`results/full/raw.jsonl.preA` (Path-A snapshot, original 8-VNF
deployer vocabulary) for audit.

## Appendix A — Walkthrough of one MAS run, metric-by-metric

To make the metric formulas concrete, this appendix takes a single
MAS row from `results/full_bmin/raw.jsonl` and reproduces every
column from first principles. The chosen row is **MAS, intent S01,
rep 0**:

```text
intent_id            : S01
prompt               : "Deploy a basic 5G core network."
complexity           : simple
ue_band              : 50
scenario             : steady
expected_vnfs        : [nrf, amf, smf, upf, ausf, udm, udr]
structured_features  : {ue_count: 50, throughput_gbps: 0.5,
                        session_count: 50, subscriber_count: 50,
                        slices: [{sst: 1}], ha_required: false,
                        autoscale_required: false}
```

Headline scored values from the row:

```text
deployment_time_s         : 139.613
config_error_rate         : 0.000
resource_accuracy         : 0.926
interventions             : 0
intent_to_deploy_accuracy : 1
policy_violation_rate     : 0.200
```

The pipeline steps that produced the input artifact (Network Planner →
Resource Allocator → VNF Configurator → Policy Validator → Deployer)
are described in chapter 4; here we focus only on the scoring layer.

### A.1 Deployment time — `139.613` s

Definition (§ 4.6.1):
```text
deployment_time_s = wall_clock_s + (deployment_wait_s or 0)
```

Inputs from this run:
- `wall_clock_s` = time from `MASRunner.run()` invocation to the LangGraph
  state machine reaching `END`. For S01 this includes:
  Network Planner LLM call (~6 s) + Resource Allocator LLM call (~4 s) +
  VNF Configurator (deterministic, <1 s) + Policy Validator LLM call (~3 s) +
  Deployer (10 helm installs at ~0.4 s each, ~4 s) ≈ **18 s**.
- `deployment_wait_s` = time the harness's `wait_for_pods_ready` blocked
  before every release reported `phase=Running` and all containers
  `ready=true`. The deployer's static 120 s sleep accounts for the bulk of
  this; for S01 ≈ **121.6 s**.

Sum: `18 + 121.6 ≈ 139.6 s`. Matches the recorded value to within
rounding.

### A.2 Config error rate — `0.000`

Definition (§ 4.6.2):
```text
config_error_rate = (# failed) / (# total) where "failed" means
                    `helm template --validate` exits non-zero.
```

The artifact for this run carries 8 `config_artifacts`, one per core
VNF. The `components.config_validation` block records the per-artifact
verdict:

```text
total      : 8
failed     : 0
per_artifact:
  oai-nrf  : ok ("validated")
  oai-amf  : ok
  oai-smf  : ok
  oai-upf  : ok
  oai-ausf : ok
  oai-udm  : ok
  oai-udr  : ok
  oai-nssf : ok
```

(The planner emitted `nssf` even though S01's `expected_vnfs` does not
include it — this becomes relevant for the Jaccard coverage in § A.5.
It does not affect Config error rate, which is purely syntactic.)

`error_rate = 0 / 8 = 0.000`.

The B-min addition of gNB and UE charts increases the validation
surface; for runs where the planner does emit them and the helm
template flags any field the OAI gNB chart's schema doesn't accept,
this metric goes up. For S01, the planner emitted core only — but a
typical post-B-min run does include gNB+UE and the row-level
`config_error_rate` is then `0.000` (all 10 OK) or `0.200` (one of
the 10 fails — usually a gNB schema strictness on multus blocks).

### A.3 Resource accuracy — `0.926`

Definition (§ 4.6.3):
```text
resource_accuracy = max(0, min(1, 1 − mean_relative_error))
mean_relative_error = mean over measured VNFs of
                      (cpu_rel_err + mem_rel_err) / 2
cpu_rel_err = |gen_cpu − opt_cpu| / opt_cpu     (clipped at the divisor)
mem_rel_err = |gen_mem − opt_mem| / opt_mem
```

The optimum (`opt_cpu`, `opt_mem`) per VNF is computed by
[`experiments/common/resource_oracle.py::compute_optimal_for_profile`](../../common/resource_oracle.py),
applying the scaling formulas from `config/vnf_resource_profiles.yaml`
to the intent's `structured_features`.

For the **UPF** with `ue_count=50, throughput_gbps=0.5`:

```text
profile.base       = {cpu: 500m, memory: 512Mi}
profile.scaling    = per_1_gbps -> {cpu: 800m, memory: 256Mi}

opt_cpu  = base + scaling × throughput_gbps
         = 500 + 800 × 0.5  = 900 m
opt_mem  = 512 + 256 × 0.5  = 640 Mi
```

The recorded delta for UPF in this run:

```text
gen_cpu = 1300m,  opt_cpu = 900m
cpu_rel_err = |1300 − 900| / 900 = 0.444
gen_mem = 768Mi,  opt_mem = 640Mi
mem_rel_err = |768 − 640| / 640 = 0.200
UPF avg = (0.444 + 0.200) / 2 = 0.322
```

The full per-VNF delta table from the artifact:

| VNF  | gen_cpu | opt_cpu | cpu_err | gen_mem | opt_mem | mem_err | avg_err |
|------|--------:|--------:|--------:|--------:|--------:|--------:|--------:|
| nrf  | 150     | 140     | 0.071   | 160     | 154     | 0.039   | 0.055   |
| amf  | 120     | 110     | 0.091   | 266     | 261     | 0.019   | 0.055   |
| smf  | 130     | 115     | 0.130   | 272     | 264     | 0.030   | 0.080   |
| upf  | 1300    | 900     | 0.444   | 768     | 640     | 0.200   | 0.322   |
| ausf | 110     | 105     | 0.048   | 134     | 131     | 0.023   | 0.036   |
| udm  | 110     | 105     | 0.048   | 134     | 131     | 0.023   | 0.036   |
| udr  | 102     | 101     | 0.010   | 130     | 129     | 0.008   | 0.009   |
| nssf | 110     | 110     | 0.000   | 134     | 134     | 0.000   | 0.000   |

```text
mean_relative_error = mean(avg_err) = 0.594 / 8 = 0.0742
resource_accuracy   = 1 − 0.0742    = 0.9258
                    ≈ 0.926                                ✓
```

Note that **UPF is the dominant contributor** to the error: the
allocator over-provisioned 1.3× the optimal CPU and 1.2× the optimal
memory because the UPF profile's scaling formula is `per_1_gbps` and
the allocator rounded a fractional throughput contribution upward.
Every other VNF is within 10 % of optimal; the allocator's behaviour
is mostly conservative-and-tight, with UPF being the weakest spot.

### A.4 Human interventions — `0`

Definition (§ 4.6.4):
```text
interventions = gates_triggered + critic_rejected + policy_fails
gates_triggered  = len(intervention_log)        — HITL gate visits the
                                                  state machine logged
critic_rejected  = 1 if not critic.would_approve else 0
policy_fails     = number of policy_checks with status == "FAIL"
```

For this run:
- The harness auto-approves both HITL gates (deployment-review and
  policy-review), so `intervention_log` is empty → `gates_triggered = 0`.
- The synthetic critic's verdict on the artifact was `would_approve =
  True`, with `reasons = []` (the recorded `critic` block).
  → `critic_rejected = 0`.
- The policy validator emitted exactly one **WARNING**
  (`root_containers`) and four **PASS**es (see § A.6 below).
  No FAILs → `policy_fails = 0`.

`interventions = 0 + 0 + 0 = 0`.

### A.5 Intent-to-deploy accuracy — `1`

Definition (§ 4.6.5):
```text
intent_to_deploy_accuracy = 1
  iff deployment_success_rate == 1.0
   ∧ vnf_coverage ≥ 0.8
   ∧ policy_decision == "GO"
   ∧ synthetic_critic.would_approve
```

Each component for this run:

**(a) deployment_success_rate.** The `deployment_results` had 8
entries (gNB and UE were not emitted by the planner for this S01
run — see the artifact); each had `status ∈ {installed, upgraded}`.
`deployment_success_rate = 8 / 8 = 1.0`. (Path-A note: any `skipped`
entries would have been excluded from both numerator and denominator
under the corrected metric.)

**(b) vnf_coverage** (Jaccard between emitted VNF types and
`expected_vnfs`):

```text
expected = {nrf, amf, smf, upf, ausf, udm, udr}    (7)
generated = {nrf, amf, smf, upf, ausf, udm, udr, nssf}  (8)
intersection = expected ∩ generated  = 7
union        = expected ∪ generated  = 8
jaccard      = 7 / 8                 = 0.875
```

The recorded `legacy.vnf_coverage = 0.875`. Threshold for
`coverage_ok` is **0.8**, so 0.875 ≥ 0.8 → True.

(For a contrasting case: in S02 rep=0 the planner additionally emits
**oai-gnb** and **oai-nr-ue**, giving union=10 and jaccard=7/10=0.7 <
0.8, so S02 fails coverage even though the deploy itself is clean.
This is what drives most of the "intent_acc=0 but everything else is
fine" cases in the data set.)

**(c) policy_decision.** The validator's static checks all returned
PASS or WARNING; no FAIL. `determine_decision` returned **GO**.
→ True.

**(d) critic.would_approve.** True (`reasons: []`).

All four components True → `intent_to_deploy_accuracy = 1`.

### A.6 Policy violation rate — `0.200`

Definition (§ 4.6.6):
```text
policy_violation_rate = 1 − policy_pass_rate
policy_pass_rate      = (# checks with status == "PASS") / (total checks)
```

The five static checks defined in
[`agents/policy_validator.py::run_static_policies`](../../../agents/policy_validator.py)
returned, for this run:

| Check               | Status   | Detail (per validator's "details" string) |
|---------------------|----------|-------------------------------------------|
| resource_limits     | PASS     | All 8 VNFs have CPU/memory limits defined |
| root_containers     | WARNING  | 8 VNFs run as root (runAsUser=0)          |
| mandatory_fields    | PASS     | All 8 VNFs have nfimage / exposedPorts / start |
| image_tags          | PASS     | All 8 VNFs use pinned image tags          |
| health_probes       | PASS     | All 8 VNFs have readinessProbe configured |

```text
PASS count = 4 (resource_limits, mandatory_fields, image_tags, health_probes)
total      = 5
pass_rate  = 4 / 5 = 0.8
violation  = 1 − 0.8 = 0.200                               ✓
```

The single non-PASS is `root_containers` returning **WARNING**, not
FAIL — the OAI charts run pods as root by design, the MAS configurator
mirrors that explicitly, and the validator flags it but does not
block. Every MAS run in the data set emits the same WARNING, which is
why MAS's `policy_violation_rate` is a constant 0.200.

(For comparison: B3 and B4 do **not** explicitly set
`podSecurityContext.runAsUser`, so their helm_values look "clean" to
this static check even though their deployed pods would also run as
root at runtime. This is the asymmetry discussed in § 4.4.)

### A.7 Putting it together

The S01 rep 0 row is therefore:

| Metric | Value | How it was computed |
|---|---:|---|
| Deployment time (s)         | 139.6 | wall-clock 18 s + pod-readiness wait 121.6 s |
| Config error rate           | 0.000 | 0 of 8 helm templates failed |
| Resource accuracy           | 0.926 | mean relative error 0.074 across 8 VNFs (UPF the worst) |
| Interventions               | 0     | no HITL gates, critic approved, no policy FAILs |
| Intent-to-deploy accuracy   | 1     | all 4 sub-conditions True (dsr=1.0, coverage=0.875, GO, critic OK) |
| Policy violation rate       | 0.200 | 1 of 5 static checks WARNING (root_containers) |

Every other row in `raw.jsonl` is computed by the same mechanical
substitution. The audit trail — per-VNF resource deltas, per-artifact
helm-template verdicts, per-check policy statuses, and the 4
intent-accuracy components — is preserved in `components.*` for every
row, so any disputed number can be re-derived from the raw data
without re-running the cluster.
